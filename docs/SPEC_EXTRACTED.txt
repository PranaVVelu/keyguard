1. Executive summary and scope
KeyGuard is a desktop-first responsive web application combining a digital-key authentication simulator,
security experiment laboratory, protocol inspector, and event analytics dashboard. Its first release
demonstrates ECDSA P-256 challenge-response authentication, credential revocation, freshness and replay
protection, and a deliberately vulnerable replay comparison in isolated lab state.

Platform Next.js/TypeScript frontend and Python/FastAPI backend
Storage SQLite for local development; PostgreSQL when hosted

Target duration 8–10 weeks at approximately 10–15 hours/week (estimate)
Primary deliverable Working end-to-end demo plus reproducible tests and documented limitations
Goals
• Show real signature verification and authorization checks.
• Allow users to inspect authentication stages and denial reasons.
• Demonstrate replay, invalid signature, expiration, cross-vehicle, and revocation tests.
• Publish reproducible security evidence and a polished accessible interface.
Explicit non-goals
• Unlocking or controlling real vehicles or handling actual vehicle credentials.
• Replicating Tesla proprietary phone-key, NFC, BLE, or key-fob protocols.
• Claiming resistance to physical relay attacks or proof of physical proximity.
• Production-grade automotive certification or a universal security score.

• Each lab requires a scoped authorization token; users must not read or mutate other labs.
• Do not log private keys, raw session secrets, or sensitive credential material.
5. Authentication protocol specification
Use established libraries with ECDSA P-256 and SHA-256. This is an educational protocol design, not a
reproduction of any manufacturer protocol. Choose one canonical, versioned encoding for signed messages;
document its exact bytes and test vectors before implementing client/server interoperability.
Protocol sequence
• 1. Client creates a P-256 key pair and registers its public key to a fictional vehicle in its authorized lab.
• 2. Client requests an unlock challenge for a specific vehicle and key.
• 3. Server creates a cryptographically random nonce and challenge ID, associates action, vehicle, key and
expiration, then stores it as unused.
• 4. Client signs the canonical message containing protocol version, vehicle ID, key ID, challenge ID, nonce,
action, and expiry.
• 5. Server verifies key status, vehicle/action binding, challenge expiry, signature validity and unconsumed
status.
• 6. Server atomically marks the challenge consumed and commits the authorized vehicle state transition.
• 7. API returns a structured decision and sanitized trace for the inspector.
Verification invariants
• Only enrolled active keys authorized for the requested vehicle/action may authenticate.
• A challenge may be used successfully at most once, including under concurrent requests.
• Expired, malformed, foreign-vehicle, action-mismatched and previously consumed challenges fail closed.
• Signed data is domain-separated and unambiguously encoded; never concatenate fields without framing.
• Cryptographic validity is necessary but not sufficient for authorization.
• Successful signature verification does not prove physical proximity; relay remains out of scope.

7. Threat model and security validation
Protected assets
• Vehicle lock state and authorization decisions; enrolled public-key registry and status; challenge freshness;
lab session boundaries; integrity of security test results.
Threats within scope
• Replaying a previously valid authentication response.
• Submitting an incorrect or tampered signature.
• Using revoked, expired or unknown credentials.
• Cross-vehicle and cross-action credential confusion.
• Double-spending a challenge via simultaneous requests.
• Accessing another user’s lab through guessed identifiers.

Each test records scenario ID, expected decision, observed decision, failure reason and timing. Distinguish
security failure (unauthorized acceptance), functional failure (valid request denied), and infrastructure failure
(untrustworthy/incomplete test). Use an atomic transaction or conditional update for challenge consumption.

Release gates
• All seven P0 features work end-to-end and the backend is authoritative.
• No known unauthorized unlock in the mandatory test suite; concurrency and cross-lab isolation verified.
• Attack lab is isolated from the hardened authentication path.
• Automated tests run in CI and failures block release.
• Threat model, architecture, test evidence and limitations are documented.
• Hosted demo has session isolation, resource limits, and event retention controls.

Development principles
• Start with a local runnable monorepo and minimal automated checks.
• Implement the security protocol and tests before visualizing successful unlocks.
• Use standard libraries and documented APIs; do not invent cryptographic primitives.
• Keep vulnerable educational logic physically separated from hardened authorization logic.
• Add typed request/response schemas, structured error codes and secure logging.
• Do not add real Tesla APIs, key fob radios, Bluetooth attacks, or proprietary integration.
• Maintain docs/DECISIONS.md for choices, assumptions and tradeoffs.
• After each milestone: run tests, report what passed/failed, update README and list remaining risks.
